# План развития Candidate Bot для нескольких IT-направлений

**Статус: интеграция реализована в feature-ветке; production не изменён.**
Решения от 2026-10-04 переопределяют конфликтующие предложения исходного
целевого плана и ограничения предыдущих этапов.

## Принятые решения интеграции (2026-10-04)

Этот раздел переопределяет конфликтующие предложения ниже. Общий versioned
реестр размещается в существующей Candidate SQLite. Источники, полный
UniversalDecision, классификации и состояния проекций записывают действующие
ingestion workers через общий сервис. Candidate worker читает реестр и пишет
личные данные, совпадения по текущей версии профиля и состояния доставки;
дополнительного Telethon-клиента не создаётся.

«Новые» сохраняет Go-ленту. «Для меня» объединяет подтверждённые совпадения
активных профилей по vacancy ID и доступно только отдельному тестовому
allowlist. Новые направления остаются shadow; доставка по умолчанию выключена.
Review, ошибки API/схемы и исчерпание бюджета не являются совпадением.
Изменение профиля пересчитывает matching локально по сохранённому анализу.

Premium/Threads допускаются в общий реестр только после существующих общих
save/publish; preview и личное сохранение кандидатом не публикуют результат.
Go-проекции сохраняют текущий порог и обязательность значимого Go-стека;
остальные направления не попадают в Go Sheets или общий Go-канал.

Одна отправка на пользователя и vacancy ID: immediate приоритетнее hourly,
manual не инициирует и не блокирует отправку. Равенство разрешает стабильный
profile ID; timezone задаёт профиль, определивший режим. Неопределённый исход
отправки автоматически не повторяется; подтверждаются только успешные страницы.
Публикация источника (published_at), обнаружение (discovered_at) и готовность
(eligible_at) хранятся отдельно; неизвестная дата не заменяется текущей.

Миграция additive: существующие карточки, callback keys, профили, версии,
черновики, архив и состояния публикации сохраняются. Прежние legacy-таблицы
не удаляются новой интеграцией. Импорт повторяемый, с dry-run; отсутствие
классификации у старой карточки не означает профильного совпадения.
Проверки этого этапа offline. Живое качество Mistral остаётся неподтверждённым
до отдельного ограниченного shadow-run. Production deployment требует
отдельного подтверждения после feature branch push и CI.

## Принятый UX-контракт профиля (2026-10-04)

Профиль в Telegram выбирается по направлению и каталожным языкам/технологиям
этого направления; экранов специализации и роли в основном мастере нет. Старые
`specialization_id`/`role_id` и снимки версий сохраняются при additive-миграции
для совместимости истории и старых шаблонов, но новые профили сохраняют пустые
legacy-поля, а matching использует направление и выбранные навыки без
назначения скрытой роли. Каталожные варианты выбираются страницами, выбор
переживает перелистывание.

Для каждого пользователя возможен не более чем один активный профиль. При
переключении активного профиля транзакция деактивирует прежние и активирует
выбранный; сохранённые вакансии, профили, версии и глобальный сбор источников
не зависят от этого переключения. Миграция не разрешает историческое состояние
с несколькими `is_active=1` автоматическим выбором: выдача и доставка закрыты
до явного выбора пользователем. Режимы grade/format остаются списочными
альтернативами; пустой список означает «любой».

Мастер редактирует одно Telegram-сообщение, сохраняет message ID в черновике и
при недоступном для редактирования старом сообщении продолжает в новом.
Неактуальный callback всегда получает answer. Надёжные даты публикации
сравниваются как абсолютные моменты UTC: «Новые» включает последние 24 часа,
«Ранее» включает нижнюю границу N дней и исключает границу 24 часа, а дата без
явного часового пояса остаётся в отдельном разделе.

## Принятое изменение общего анализа (2026-10-03)

Универсальный этап анализа по `it_roles.v1.json` принят для уже работающих
источников live/history, Premium Search и Threads. Для классификации применяется
строгий контракт `vacancy-analysis.v1` / `catalog-classifier.v1`; обязательный
стек отделён от предпочтительного. Универсальный режим включён по умолчанию,
`LEGACY_GO_ANALYSIS=true` сохраняет прежний Go-контракт. Префильтр пропускает
общие признаки найма и ролей, отсекая очевидные резюме и продвижение курсов.
Лимит Mistral общий для процессов, атомарно хранится в Premium SQLite и по
умолчанию равен 1000 вызовам за UTC-день. Универсальный запрос не повторяется;
ошибки, неоднозначность и исчерпание лимита не являются совпадением и не
экспортируются основным pipeline.

Это решение supersedes раннее ограничение этапа 1, что профили не влияют на
анализ, а Mistral-поведение основного мониторинга остаётся Go-only. Оно не
меняет Candidate интерфейс, правила публикации или deployment. Качество
проверяется на десяти синтетических размеченных примерах с моками; такой отчёт
показывает ошибки prefilter-классификации и не оценивает живые ответы модели.

## Принятое решение для этапа 1 (2026-10-03)

Этап 1 реализует каталог специальностей и внутреннее управление несколькими
карьерными профилями на пользователя в существующей `candidate_bot.sqlite3`.
Профили пока не влияют на анализ, классификацию, фильтрацию или рассылку.
Candidate Bot на этом этапе предоставляет только ленту, действие «Сохранить»
и архив сохранённых вакансий. Отклики, скрытие, жалобы, личный поиск и
соответствующие callbacks/данные удаляются. При миграции прежние `saved`
переносятся в отдельный архив с исходным `updated_at`; остальные действия,
заметки, жалобы и browser sessions удаляются. Вакансии, callback keys,
channel delivery state и опубликованные сообщения сохраняются. Старые
сообщения Telegram не редактируются, а callbacks их устаревших кнопок не
поддерживаются.

Один профиль описывает один путь «направление → специализация → роль»;
списочные предпочтения допускают несколько значений и пустое состояние.
Изменения профиля записываются неизменяемыми версиями. Удаление профиля
удаляет и его версии. Используется один версионируемый JSON-каталог и одна
общая Candidate SQLite. Начальный каталог охватывает разработку, QA, Data/AI,
аналитику, дизайн, DevOps/администрирование, безопасность, менеджмент,
HR/рекрутинг, маркетинг и контент. Язык текста вакансии отделён от языков
программирования; часовой пояс по умолчанию `Europe/Moscow` и проверяется как
IANA timezone. Telegram-интерфейс профилей не входит в этап.

Это решение ограничивает только личный Candidate Bot на первом этапе; оно не
меняет Mistral-анализ и рассылку основного мониторинга. Production не
затрагивается.

## Цель и исходное состояние

Candidate Bot должен стать персональным помощником по вакансиям для нескольких
IT-направлений. Пользователь задаёт одно или несколько направлений, получает
вакансии из уже работающих источников, может искать по ним и вести личный статус
по каждой вакансии. Направления — классификация и фильтр в одном общем реестре,
а не отдельные базы или копии одной вакансии.

Сейчас основная Telegram-мониторинговая цепочка обрабатывает Go/Golang:
`VacancyProcessor` применяет Go-prefilter, вызывает общий анализ Mistral, пишет
в два Google Sheets, отмечает успешные экспорты в `data/state.jsonl` и
публикует в Candidate Bot, если включена публикация. Telegram ID строится из
источника и сообщения. JSONL хранит URL и ID бессрочно, hash нормализованного
текста — по TTL (по умолчанию 30 дней); claims в SQLite защищают от
конкурирующей обработки. Успешным экспорт считается после записи в оба листа.

Candidate Bot работает отдельным Bot API long-polling процессом. Его
`data/candidate_bot.sqlite3` хранит опубликованные карточки, состояния доставки,
личные действия и жалобы пользователей, а также состояние однокарточной
навигации. Статусы на пользователя: `new`, `saved`, `applied`, `replied`,
`interview`, `offer`, `rejected`, `hidden`. Они не должны стать общими
атрибутами вакансии и не должны теряться при переходе к нескольким
направлениям.

Premium Global Search уже исполняется live-процессом на общей Telethon-сессии,
содержит track abstraction (пока зарегистрирован только `go`), строгий анализ
Mistral, ранжирование, preview/save/publish, ручные решения и собственный
SQLite для истории и очереди. Общий `/search` использует существующие
Candidate-карточки, Premium Search и, при настройке, Threads API; личный
Candidate `/search` пока создаёт preview-запуски и не превращает результаты в
общий архив автоматически. Источники и workers нельзя дублировать в Candidate
процессе: ему следует потреблять результаты/карточки через общий сервис или
проекцию.

## Целевая архитектура

### 1. Каталог направлений

Завести версионируемый каталог с неизменяемым ключом направления (`go`,
`python`, `frontend`, `devops` и т. п.), локализованной меткой, алиасами,
правилами prefilter, признаками ролей, инструкциями Mistral, порогами
уверенности и версией правил. Начальный набор расширяется отдельными решениями;
план не предполагает автоматического включения неподдержанных стеков.
Каталог должен отделять общие признаки вакансии от track-specific результата.

Профиль пользователя хранит подписки/предпочтения по ключам направлений и
настройки выдачи. Одна вакансия может соответствовать нескольким направлениям.
Связь «вакансия — направление» хранится как many-to-many с confidence,
решением (`accepted|review|rejected`), причиной и версией классификатора.
Пользователь может включать/выключать направление без копирования карточки.

### 2. Общий реестр вакансий

Ввести единый source-neutral Vacancy Registry с одной сущностью вакансии и
отдельными таблицами источников, track classification и проекций. Реестр
должен быть общим для всех направлений и всех источников; не создавать
`go.sqlite`, `python.sqlite` и аналогичные базы. Физическое размещение и
владелец SQLite должны быть выбраны до первого этапа реализации. Предпочтение:
одна versioned SQLite база реестра, принадлежащая live worker для записи;
Candidate Bot и admin API обращаются через существующие сервисные границы и
не открывают параллельный Telegram client.

Минимальная логическая модель:

- `vacancies`: внутренний ID, общие нормализованные поля Mistral, время первой
  фиксации и последнего обновления;
- `vacancy_sources`: source type, внешний ID, каноническая ссылка, дата,
  канал/автор как metadata, raw-text fingerprint; уникальность по
  `(source_type, external_id)` и пригодные exact keys;
- `vacancy_tracks`: `vacancy_id`, track key, решение, confidence, причина,
  версия правил и время;
- `vacancy_projections`: состояние доставки/экспорта в Sheets, Candidate
  публикацию и иные действующие представления, с retry/recovery metadata;
- существующие Candidate personal actions и reports остаются отдельными
  таблицами или совместимой проекцией с теми же ключами пользователя и вакансии.

Репосты, доказанные текущими строгими правилами `vacancy_groups`, могут
указывать на одну каноническую vacancy и несколько source records. Сходство
текста или общий стек сами по себе не основание для объединения.

### 3. Ingestion и анализ источников

Сохранить источники и их текущих владельцев:

- Telegram live/history продолжает получать сообщения Telethon и передавать
  их через общий ingestion contract. Для Go сохраняются текущие критерии и
  выходные Sheets;
- Premium Global Search остаётся в live worker и использует уже имеющуюся
  Telethon session. Его очередь, квоты, run history, callbacks и ручные
  действия продолжают работать;
- Threads остаётся опциональным источником общего `/search` и не становится
  обязательным для Candidate Bot;
- новые уже реализованные интеграции подключаются адаптерами, которые
  создают общий source item; отдельные источники вакансий внутри Candidate
  Bot не реализуются.

После source-specific безопасного prefilter track analyzer вызывает текущий
Mistral API/модель и сохраняет общий `VacancyAnalysis` плюс результат
классификации направления. Mistral остаётся единственным LLM-провайдером в
этом плане. Строгая схема, ограниченные повторы, защита от prompt injection,
причины решения и состояния неопределённости сохраняются. Неуверенный
результат помечается `review`, а не молча отбрасывается или показывается как
точное совпадение.

### 4. Candidate Bot как пользовательская проекция

Личный бот получает единый каталог вакансий, фильтрует его по подпискам
пользователя, статусу и выбранным источникам/направлениям. Поиск, карточки,
жалобы и пользовательские статусы используют один vacancy ID независимо от
того, из какого направления или источника карточка открыта. Одновременное
совпадение с несколькими направлениями не создаёт повтор карточки.

Существующие разделы «Новые», «Мои отклики», «Сохранённые», «Скрытые»,
навигация одной редактируемой карточкой, кнопки статусов и приватность жалоб
сохраняются. Добавляются выбор направлений и фильтр/подпись направления.
Миграция не меняет значения существующих статусов; ранее скрытая/отмеченная
карточка остаётся в том же личном состоянии. Отображение старых карточек при
пустом профиле направлений должно быть безопасным и детерминированным
(рекомендуется временно считать подпиской `go`, пока пользователь не выбрал
профиль).

## Данные и миграция

Миграция должна быть additive, идемпотентной и проверяемой до переключения
чтения. Не удалять исходные SQLite, JSONL или Sheets в рамках перехода.

1. **Снять baseline.** Зафиксировать количество и ключи записей Candidate,
   статусы по пользователям, delivery states, группы репостов, JSONL dedupe
   keys и Sheets totals. Секретные данные и vacancy text не копировать в логи.
2. **Создать версию схемы реестра.** Таблицы создаются пустыми, с foreign keys,
   WAL, busy timeout, транзакционными миграциями и уникальными индексами.
3. **Импортировать источники истины.** Сначала Telegram/вакансии из Candidate
   SQLite и доступных локальных опубликованных результатов; затем Premium
   сохранённые/опубликованные результаты и Threads/общий поиск, если они
   содержат стабильный внешний ID и допустимый анализ. Исторические Sheets
   не импортировать автоматически до отдельного решения: там нет полного
   source metadata и user actions.
4. **Перенести Candidate-действия без преобразования.** Сохранить точные
   `telegram_user_id`, vacancy ID, статус, заметку и timestamps. Reports,
   callback keys, browser sessions и channel delivery markers перенести
   отдельно. Callback keys заново вычислять нельзя без совместимости старых
   callbacks; предпочтительно сохранять имеющиеся значения.
5. **Внести dedupe keys.** Импортировать все бессрочные Telegram links/IDs из
   `state.jsonl` и актуальные text hashes с исходными timestamps/TTL. JSONL
   остаётся append-only совместимым зеркалом до отдельного решения. Неполные
   события не восстанавливать как полноценные вакансии. Стабильные ID
   Premium/Threads импортировать через `(source_type, external_id)` без
   подмены Telegram ID.
6. **Dual-write и сверка.** Новые обработки атомарно записывают vacancy/source/
   track rows и продолжают текущие side effects. Сверять количества, ключи,
   дубли и статусы; несовпадения блокируют cutover.
7. **Переключать чтение по одному пути.** Сначала Candidate «Новые» и поиск,
   затем Premium actions/publication и admin search. У каждого шага есть
   feature flag и процедура отката к прежнему read path. Повторный импорт
   безопасен.
8. **Завершить миграцию только после периода сверки.** Оставить SQLite legacy,
   Sheets и JSONL для отката и аудита. Их удаление/прекращение записи — отдельное
   утверждаемое изменение.

Для существующих уже отмеченных вакансий миграция Candidate не должна заново
публиковать карточки. Неопределённые `sending` состояния трактуются по текущему
правилу: не отправлять повторно автоматически; предусмотреть сверку вручную.

## Этапы реализации

1. **Контракты и каталог.** Описать source-neutral item, track definition,
   классификацию и реестр ключей. Добавить контрактные тесты; пользовательский
   интерфейс и live behavior не менять.
2. **Реестр и импорт.** Добавить versioned schema, транзакционный importer,
   dry-run отчёт и сверку. Провести импорт на копии данных и проверить
   идемпотентность; старый бот остаётся источником выдачи.
3. **Go dual-write.** Подключить текущий Telegram Go pipeline к реестру и
   существующим Sheets/JSONL/Candidate publisher. Никакого изменения фильтра,
   статусов, ID или публикационной политики Go.
4. **Candidate read cutover.** Перевести личные списки на registry join с
   personal actions. Проверить мигрированные статусы и поведение callback.
5. **Premium integration.** Заменить внутреннюю связанность Premium с
   `VacancyProcessor` на явные contracts; записывать результаты в общий
   реестр, сохраняя runs, квоты, ранжирование, ручные действия и API.
6. **Второе направление в shadow mode.** Выбрать одно направление, добавить
   его правила Mistral, классифицировать без показа/публикации; измерить
   качество на размеченной выборке и скорректировать пороги.
7. **Ограниченный beta и расширение.** Включить направление пользователям по
   явному профилю, сначала только preview, затем обычные личные карточки.
   Публичная публикация/экспорт за пределы личного бота остаётся отдельным
   решением на направление. Подключать следующие направления по одному.
8. **Стабилизация.** Сверить реестр, dedupe, Sheets, Premium и действия
   пользователей; удалить флаги/старые пути только после согласованного окна
   наблюдения и отдельного утверждения.

## Риски для существующего Go-бота и меры

| Риск | Последствие | Мера |
|---|---|---|
| Изменение общего Mistral prompt/схемы меняет классификацию Go | Пропуски или лишние Go-вакансии | Зафиксировать Go fixture corpus и решения; track prompt versioning; Go остается на прежнем пороге до отдельной калибровки |
| Изменение ID или dedupe scope | Повторные карточки/экспорты либо пропуски | Оставить Telegram ID, вечные link/ID и 30-дневный hash TTL; уникальные claims и compatibility tests |
| Dual-write не атомарен с Sheets/Bot API | Реестр и внешние проекции расходятся | Projection states, idempotency keys, retry/reconciliation; не считать export завершённым до обоих Sheets |
| Несколько процессов пишут общий SQLite | lock contention или потерянные действия | Один владелец записи/сервисный API, короткие транзакции, WAL и busy timeout; не открывать Telethon в Candidate worker |
| Неверное объединение межстековых вакансий | Вакансия скрывает самостоятельный отклик | Сохранять source records; строгая текущая логика групп; стек не использовать как identity |
| Миграция Candidate теряет этап отклика | Пользователь теряет личную историю | Копировать действия и timestamps без нормализации; сверка per-user counts и статусов до cutover |
| Повторная публикация после восстановления | Дубли в общем beta-канале | Перенос delivery state и channel message ID; `sending` считать неопределённым и не повторять автоматически |
| Premium/Threads задерживают live worker | Задержка мониторинга Telegram | Сохранить приоритеты/лимиты существующей очереди, бюджет и метрики задержки; новые треки ограничивать concurrency |
| Отраслевой prefilter пропускает вакансии | Неполная выдача направления | Shadow mode, измерение precision/recall и ручная выборка перед включением |
| Направления смешиваются в личной выдаче | Плохая релевантность и дубли | Явные подписки, join по общей vacancy ID, отдельные classification rows; один результат на карточку |

## Критерии приёмки будущей реализации

- Существует один общий versioned registry со связями many-to-many между
  вакансиями и направлениями; отдельные базы на стек отсутствуют.
- Одна вакансия, найденная мониторингом, Premium и/или несколькими треками,
  отображается один раз и сохраняет ссылки на все доказанные источники.
- Go monitoring сохраняет прежние prefilter/Mistral threshold, Telegram ID,
  Sheets формат и порядок подтверждения экспорта; повторно обработанные
  ссылки/ID блокируются бессрочно, text hash — в прежний TTL.
- Premium Global Search сохраняет доступность, очередь live worker, квоты,
  историю, статусы результатов, ручные actions и preview/save/publish.
- Все существующие Candidate user statuses, notes, reports, callbacks и
  delivery states переживают importer без изменения значений и без повторной
  публикации.
- Пользователь управляет несколькими направлениями; для одного направления
  доступны новые вакансии, поиск и личные действия. Отключение направления не
  удаляет карточку, дедупликацию или историю действий.
- Mistral использует строгую версионируемую классификацию; review не
  маскируется под accepted. Ошибка одного источника/направления не блокирует
  остальные.
- Importer повторяем; dry-run показывает счётчики и расхождения без изменения
  данных; backup/restore и rollback к прежнему чтению документированы.
- Тесты покрывают schema upgrades, importer idempotency, mapping статусов,
  exact dedupe/TTL, concurrent claims, частичный Sheets export, Premium
  recovery, Telegram session ownership и multi-track выдачу.
- Переключение на новый read path происходит только после совпадения
  сверочных счётчиков и успешной проверки мигрированных личных статусов.

## Решения, требующие утверждения

Перед этапом 1 нужно согласовать начальный перечень направлений и решить,
какие из Threads и локально найденных, но не опубликованных Premium результатов
становятся постоянными записями общего реестра. Отдельно утвердить физическую
локацию реестра и то, какие направления могут публиковаться в общий канал.
Предложение этого плана: один registry SQLite как общая сущность, владелец
записи — live worker; Candidate по умолчанию показывает только явно выбранные
трековые карточки, а Go сохраняет текущий production path и экспорт до
завершения dual-write сверки.
