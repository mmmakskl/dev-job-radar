# Candidate registry: эксплуатация, миграция и откат

Направление 1С доступно допущенным пользователям Candidate Bot через личную
ленту и автоматическую личную доставку после включения флага. Новые таблицы находятся в той
же Candidate SQLite; отдельной базы на направление и нового Telethon-клиента нет.
Ingestion workers записывают источники/анализ/проекции; Candidate worker
использует сохранённый анализ для matching и пишет личный архив/доставки.

## Доступ и готовые сценарии

| Сценарий | Условие |
| --- | --- |
| Профильные возрастные экраны, сохранение и архив | Существующие `CANDIDATE_BOT_*` настройки и один активный профиль для выдачи |
| Редактор нескольких профилей и шаблонов | Доступ к Candidate Bot |
| «Для меня» | Любой пользователь в `CANDIDATE_BOT_ALLOWED_USER_IDS` с одним явно выбранным активным профилем; совпадения должны быть подтверждены |
| 1С карточки | Любой допущенный пользователь с активным совпавшим профилем; общая Go-публикация отключена |
| immediate/hourly уведомления для всех треков | `CANDIDATE_PROFILE_DELIVERY_ENABLED=true`, `CANDIDATE_BOT_ALLOWED_USER_IDS` и активные совпадения |
| Поиск по снимку профиля | `CANDIDATE_CATALOG_SEARCH_ENABLED=true`, оба allowlist, включённый Premium и работающий live worker |
| Общий Premium Go / Threads search | Прежние флаги, квоты и настройки источников |

Автоматическая доставка и Premium catalog preview по умолчанию выключены,
профильный allowlist пуст и применяется к Premium preview. Все направления
доступны через подтверждённые совпадения активного профиля. Go-проекции допускают только значимый обязательный
Go-стек с confidence не ниже существующего порога 90. Backend/API-роль и
предпочтительный Go не являются доказательством Go-вакансии. Общие действия
save/publish не превращают universal review/недоступный анализ в подтверждённый
результат; такие записи требуют нового достоверного анализа.

Для проверки после разрешённого rollout: создать профиль, выбрать шаблон,
проверить запрос, запустить preview, открыть результаты и отменить другой
запуск. Повтор кнопки не создаёт второй run. Сохранить один результат в личный
архив и проверить его отсутствие в общей Go-ленте. Для «Для меня» проверить
один выбранный активный профиль и отсутствие карточки у другого владельца.
Не включать массовую доставку для этой проверки.

## Offline import и сверка

Обычный запуск скрипта — dry-run. Candidate копируется SQLite backup API во
временную базу; Premium/Search открываются read-only. Исходные данные не
мигрируются dry-run. Логи содержат только счётчики, без текстов и идентификаторов.

```bash
PYTHONPATH=src venv/bin/python scripts/migrate_candidate_registry.py \
  --candidate-db /secure/data/candidate_bot.sqlite3 \
  --premium-db /secure/data/premium_search.sqlite3 \
  --search-db /secure/data/admin/admin.sqlite3 \
  --state-jsonl /secure/data/state.jsonl --text-hash-ttl-days 30
```

Импорт включает старые общие Candidate-карточки и только сохранённые или
опубликованные общие Premium/Threads результаты. Preview и личный архив не
дают допуска в общий реестр. Отсутствующий полный анализ хранится как
недоступный, без выдумывания классификаций или профильных совпадений.
`--state-jsonl` импортирует только успешные `exported` события: точные ссылки
и построенные из них ID бессрочно, text hashes — пока не истёк указанный TTL.
Отчёт показывает число ключей без текстов и идентификаторов. Повторный импорт
идемпотентен; исходный JSONL не изменяется и остаётся текущим источником
дедупликации.
Известная дата источника сохраняется; пустая дата повторного импорта её не
затирает. Legacy callbacks, profile versions, drafts, archive и delivery states
не пересоздаются. Exact source ID/URL может объединить источник; сходство
текста или стека не объединяет вакансии.

Перед применением в production после отдельного разрешения остановить
записывающие workers, согласовать окно backup и снять согласованный snapshot.
`--backup` использует online SQLite backup API, включая WAL, и отказывается
перезаписывать существующий файл:

```bash
PYTHONPATH=src venv/bin/python scripts/migrate_candidate_registry.py \
  --candidate-db /secure/data/candidate_bot.sqlite3 \
  --premium-db /secure/data/premium_search.sqlite3 \
  --search-db /secure/data/admin/admin.sqlite3 \
  --state-jsonl /secure/data/state.jsonl --text-hash-ttl-days 30 \
  --backup /secure/backups/candidate-before-registry.sqlite3 --apply
```

Для согласованного восстановления всей системы в том же остановленном окне
сохранить Premium, admin и groups SQLite через SQLite backup API, а также
append-only JSONL и claims; не копировать один `.sqlite3` мимо активного WAL.
Backup содержит персональные данные и хранится вне Git с ограниченным доступом.
Этот этап разработки не снимал backup production и не подключался к нему.

Повторить dry-run и apply на копии: количество новых registry vacancies должно
стать нулевым, ключи/исторические timestamps и личные данные должны совпасть,
`integrity_check=ok`, foreign-key violations — 0. До cutover сравнить по каждой
таблице количества, стабильные ключи, версии профилей, callback keys, личный
архив, channel message IDs и delivery states. CI проверяет повторную миграцию
и restart на синтетических SQLite fixtures; это не сверка production-данных.

## Отправки и восстановление

Ключ уведомления зависит только от владельца и vacancy ID. Смена профиля, его
версии, режима или перезапуск не создают повтор. Отправка использует только
единственный явно выбранный активный профиль пользователя; его режим задаёт
immediate/hourly/manual, а timezone берётся из этого профиля. Состояние старых
пользователей с несколькими активными профилями блокирует выдачу до явного выбора.

Очередь резервирует каждую страницу транзакционно. После успешного ответа
Bot API подтверждаются только вакансии этой страницы. Явный отказ возвращает
их в pending; сетевой timeout и сбой между send/ack оставляют unknown/sending.
Их нельзя автоматически возвращать в pending: сначала сверить с Telegram.
Для общего канала действует та же граница: явный отказ Bot API освобождает
заявку, а timeout оставляет `sending` до ручной сверки публикации.
Неиспользованное резервирование без начала send может быть освобождено после
таймаута. История уведомлений и сохранённые карточки не удаляются при
отключении профиля.

`published_at` — дата исходного сообщения, `discovered_at` — обнаружение,
`eligible_at` — готовность. Дайджест планируется по готовности и показывает
дату публикации. Неизвестная дата показывается явно.

## Feature branch, release и rollback

Проверки выполняются на `feature/candidate-registry-integration`; push в
`master` запрещён в этом этапе, поскольку он запускает production deployment.
Релиз — только по отдельному подтверждению через существующий CI/CD.
Перед релизом нужен описанный выше backup и сверка миграции на копии.
После релиза проверить SHA образа, heartbeat/health bot, admin и candidate,
состояния очереди без повторов и один разрешённый личный сценарий.

Для отключения доступа к 1С откатить Candidate Bot на предыдущий образ штатным
CI/CD и проверить его heartbeat. Для отката Premium preview и персональной
доставки отключить соответствующие флаги и очистить profile allowlist. При
необходимости вернуть предыдущий образ существующим CI/CD; `LEGACY_GO_ANALYSIS=true` возвращает
прежний анализ Go. Additive-таблицы не удалять. При аварийном восстановлении
базы остановить writers и восстановить согласованный набор backups; сначала
сверить unknown/sending доставки, чтобы не создать повторную публикацию.
